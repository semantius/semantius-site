Access in Semantius is decided inside the database. Each entity names the permission needed to read its records and the one needed to write them, and row-level security on the entity's table checks the caller's permissions on every request, whichever client sends it.

| Concept | What it is |
|---|---|
| Permission | A name such as `crm:read`. It belongs to a module. |
| Role | A named set of permissions, assigned to users. |
| Direct grant | A permission given to one user without a role. |
| Hierarchy entry | "A includes B": holding A grants B as well. |

A user's permissions are the permissions of all their roles, plus their direct grants, plus everything those include through the hierarchy, at any depth. A disabled user holds none. Roles are flat: a role cannot contain another role, so build broader access with the hierarchy instead.

These are Semantius roles, kept as data. The PostgreSQL roles a request runs as are a separate thing, described under [pg_semantius roles](/docs/pg-semantius/reference#roles).

## Permissions

| Column | Meaning |
|---|---|
| `permission_name` | The permission and its key. Colon-separated segments of `a-z`, `0-9`, `-` and `_`, each starting with a letter or digit, such as `crm:read` or `service-catalog:view` (23514). No spaces, dots or capitals. |
| `description` | What the permission allows. |
| `module_id` | The module it belongs to. Required: deleting the module deletes its permissions, with their grants. |

- **Every new permission is granted to the Administrator role** when it is created.
- **Renaming a permission** carries the new name to every entity, module, grant and hierarchy entry that names it, and rebuilds the access policies of those entities. Names inside rules, such as `{"has_permission": "crm:read"}`, are not rewritten: a rule that names the old permission then answers false for everyone.
- **Deleting a permission** that an entity uses is refused (`23503`, or `23001` on PostgreSQL 18).

Names such as `crm:read` and `crm:manage` follow a convention of the modeling tools, `<module_slug>:<verb>`. The platform does not derive them; a permission belongs to its module through `module_id`.

## Roles

| Column | Meaning |
|---|---|
| `role_name` | The role's name, unique. |
| `slug` | A unique identifier of `a-z`, `0-9` and `_`. Left empty, it is derived from the name. |
| `description` | What the role is for. |
| `module_id` | The module the role belongs to, or none. Deleting the module deletes the role and its assignments. |
| `origin` | `user` (the default), `model`, `model_master` or `system`: how the role was created. Set on insert and never changed (90203). |
| `catalog_role_code` | The catalog persona the role was built from. Write-once (90206). |

A role gets its permissions through `role_permissions` and its users through `user_roles`; a user gets a direct grant through `user_permissions`. Each row records when (`granted_at`, `assigned_at`) and by whom (`granted_by`, `assigned_by`, the calling user unless the request names another). Their ids are generated from the pair they join: `1001.10001` for user 1001 in role 10001, `10001.helpdesk:manage` for a grant.

```bash
# A role for helpdesk agents, in the module with id 1001
semantius call crud create_role '{"data":{"role_name":"Helpdesk Agent","module_id":1001}}'

# Grant it a permission, by name
semantius call crud create_role_permission '{"data":{"role_id":10001,"permission_name":"helpdesk:manage"}}'

# Assign it to a user
semantius call crud create_user_role '{"data":{"user_id":1001,"role_id":10001}}'
```

Direct grants have no tool of their own: write them to `/user_permissions` with `postgrestRequest`.

## The hierarchy

A `permission_hierarchy` entry names an `including_permission_name` and an `included_permission_name`. Holding the including permission grants the included one, and everything that one includes in turn:

```bash
# Whoever may manage the helpdesk may also read it
semantius call crud create_permission_hierarchy '{"data":{"including_permission_name":"helpdesk:manage","included_permission_name":"helpdesk:read"}}'
```

The direction matters: the broader permission includes the narrower one, never the reverse. An entry that includes itself (23514), repeats another (23505), closes a cycle (90210) or makes a chain longer than eleven entries (90211) is refused.

## How entities use permissions

Every entity has a `view_permission` (default `public:read`) and an `edit_permission` (default `admin`). Its table's policies check them as follows:

| Operation | Without a `select_rule` | With a `select_rule` |
|---|---|---|
| Read | `view_permission` | The rule |
| Insert | `edit_permission` | `edit_permission` |
| Update, delete | `edit_permission` and `view_permission` | `edit_permission` and the rule |

- **`public:read` is not anonymous.** Every signed-in user holds it, so a new entity can be read by everyone who signs in and written only by administrators.
- **Writers need the view permission too.** An update or delete without it reaches no record and changes nothing, without an error. An insert that asks for the new record back, as the MCP tools always do, is refused with `42501`.
- **A refused read is empty, not an error.** A user without the view permission gets no records.
- **One permission covers every write.** To let only some writers delete, approve or close, add a [validation rule](/docs/business-logic/extensions#validation_rules) that tests `$mode` and [`has_permission`](/docs/business-logic/extensions#check-the-current-users-permission-has_permission). To filter rows per user, use a [`select_rule`](/docs/business-logic/extensions#select_rule).
- **The schema follows the permissions.** An entity's `entities` row, its fields and its schema are visible only to holders of its `view_permission`, its `edit_permission` or `admin`. Anyone else gets `404` from `/rpc/get_schema`, the same answer as for an entity that does not exist. A user whom a `select_rule` lets read rows, while holding neither permission, reads the rows but not the schema.
- **A cascade does not check the children.** Deleting a parent deletes its `cascade` children whatever the deleting user's rights on them. See [Relationships](/docs/entities#relationships).
- **A module's permission is not passed down.** A module's `view_permission` decides who sees the module, not who reads its entities. See [Modules](/docs/modules).

Changing an entity's `view_permission`, `edit_permission` or `select_rule` takes `admin`, and rebuilds its policies at once.

## Built-in roles and permissions

Every instance starts with four permissions in the administration module, two hierarchy entries and two roles:

| Permission | Includes | What uses it |
|---|---|---|
| `public:read` | | The default `view_permission` of a new entity. |
| `user:read` | | Reading users, and the default `view_permission` of a new module. |
| `user:manage` | `user:read` | Creating, changing, disabling and deleting users. |
| `admin` | `public:read` | The platform's own entities: modules, entities, fields, roles, permissions and the [audit logs](/docs/audit-logs). The default `edit_permission` of a new entity. |

| Role | Permissions | Who has it |
|---|---|---|
| User (id 1) | `user:read`, `public:read` | Every user, automatically. A user cannot lose it (90103). |
| Administrator (id 2) | `user:manage`, `public:read`, `admin`, and every permission created later | The first user to sign in, and whoever an administrator assigns. |

- **`admin` is not a wildcard.** Administrators hold every permission because each new one is granted to the Administrator role when it is created. A permission taken away from that role stays away, and a user who holds `admin` through another role, or directly, does not gain the other permissions. They can grant themselves any of them, though: see [Who can manage access](#who-can-manage-access).
- **Both roles can be renamed.** Their slugs, `user` and `administrator`, cannot change (90204).
- **Every signed-in user can read every user**, email included, because the User role holds `user:read`.
- **`user:manage` is not `admin`.** It lets a user create, edit, disable and delete users, but not assign roles, set a user's `external_id` (90107) or create API keys for others.

## Who can manage access

Reading and writing `roles`, `permissions`, `role_permissions`, `user_roles`, `user_permissions` and `permission_hierarchy` takes `admin`. Anyone else reads an empty list from them, an insert is refused with `42501`, and an update or delete changes nothing. To see their own roles and permissions, a user calls `/rpc/get_userinfo`.

There is no rule that a user may only grant what they hold: anyone with `admin` can grant any permission and assign any role, Administrator included.

These guards keep an instance administrable. Each is refused with `42501` (HTTP 403) and carries its code in the hint:

| Code | Refused |
|---|---|
| `90103` | Removing the User role from a user. Deleting the user removes it with them. |
| `90104` | Leaving the instance without an enabled Administrator: removing the role from its last holder, disabling or deleting that user, or deleting the role. |
| `90107` | Setting or changing a user's `external_id` without `admin`. Sending the unchanged value is allowed. |
| `90108` | Removing `admin` from the Administrator role, or deleting or renaming the `admin` permission. |

## When a change takes effect

A user's permissions are worked out once per request, at its first check. A grant, a revoke, a role change or a disabled account applies from the user's next request. Sign-in tokens carry no roles or permissions, so nobody has to sign in again.

## Users and sign-in

A user is identified by `external_id`, the subject of their sign-in token (for Microsoft Entra ID, `entra.<tid>.<oid>`). The first request of a new user must be `POST /rpc/get_userinfo`, which creates their user record; until then every request fails with `42501` and the hint code 90006. The app and the CLI make that call for you. Each later call copies the email and names from the token into the record.

- **`is_disabled`.** A disabled user holds no permissions, and every request fails with hint code 90006.
- **`is_agent`.** An agent is a user like any other, with the User role.
- **No anonymous access.** Every request to data or to a function needs a signed-in user.

An **API key** acts as its owner, with every permission the owner holds at the time of each request. It has no scope and no expiry. A disabled user's keys stop working until the user is enabled again, and deleting a user deletes their keys.

| Call | What it does |
|---|---|
| `/rpc/generate_api_key` | Creates a key and returns it once. `p_user_id` `0` creates one for yourself (prefix `uk-`); any other user id takes `admin` (prefix `sk-`). `p_description` is optional. |
| `/rpc/list_api_keys` | The keys of `p_user_id` (default `0`, yourself), without their secrets. Another user's keys take `admin`. |
| `/rpc/delete_api_key` | Deletes the key `p_key_id`. |

The MCP tools `generate_api_key`, `list_api_keys` and `delete_api_key` make the same calls.

## API

| Call | What it does |
|---|---|
| `/permissions`, `/roles`, `/role_permissions`, `/user_roles`, `/permission_hierarchy` | The access model, through the `create_*`, `read_*`, `update_*` and `delete_*` tools of each, or `postgrestRequest`. |
| `/user_permissions` | Direct grants, through `postgrestRequest`. |
| `/rpc/get_userinfo` | The caller's profile, roles, effective permissions (the hierarchy applied) and visible modules. The MCP tool `getCurrentUser` calls it. |
| `/rpc/has_permission` | Whether the caller holds `p_permission_name`. An unknown name answers false. |

## Errors

| Code | Meaning |
|---|---|
| `42501` | A refused write, or one of the guards above (see its hint code). With hint code 90101, a call that requires a permission the caller lacks; the hint names the permission. |
| `90203`, `90205` | A role's or hierarchy entry's `origin` cannot change. |
| `90204` | A system role's slug cannot change. |
| `90206` | `catalog_role_code` is write-once. |
| `90210` | The hierarchy entry would close a cycle. |
| `90211` | The hierarchy entry would make a chain longer than eleven entries. |
| `90401`, `90402` | The user or the API key does not exist. |
| `23514` | A permission name or role slug breaks its pattern, or a hierarchy entry includes itself. |
| `23505` | A role name, role slug, grant, assignment or hierarchy entry already exists. |
| `23503`, `23001` | A permission or role is still in use by an entity, a module or a RACI event. |
